# 블로그 이전 및 웹 관리자 작업 기록

마지막 확인: 2026-11-05 (KST) · 상태: GitHub 단독 방식 배포 및 실제 발행 검증; 테스트 정리 배포 중

> 정정: 별도 API 호스팅은 필수가 아니다. 브라우저에서 본인이 입력한 GitHub fine-grained PAT로 GitHub API를 직접 호출하면 GitHub만으로 가능하다. 다만 GitHub 로그인 버튼과 다른 사용 경험이고 토큰을 브라우저에서 다루는 위험이 있다. 아래 Worker 관련 내용은 선택지이며 채택된 결정이 아니다.

## 목적과 완료 기준

기존 글과 주소를 보존하면서 TanStack Start 정적 블로그와 웹 관리자를 구축한다. 본인이 웹에서 GitHub로 로그인하고 MDX 글을 작성·수정·미리보기·발행하면 GitHub 커밋, Actions 빌드, GitHub Pages 배포까지 이어진다. 실제 배포 환경에서 이 흐름과 실패 처리를 확인해야 완료다.

## 현재 확인된 사실

- 로컬 저장소 remote: `https://github.com/lebmouse/my-blog.git`이며 GitHub에서 `lebmouse/lebmouse.github.io`로 연결됨. 브랜치 `main`. 실제 Pages 주소는 `https://lebmouse.github.io/`이고 source는 GitHub Actions로 확인.
- Next.js 15, React 19, TypeScript, Panda CSS, 파일 기반 MDX. GitHub Actions는 main push 시 Next 빌드 후 Pages에 배포하도록 작성됨. 실제 실행 및 Pages 설정은 미확인.
- 기존 MDX 4개는 `description`이 없다. `about-blog.mdx`는 `MainColorTheme` React 컴포넌트를 사용한다. 콘텐츠와 기존 `/posts/{slug}` 주소 유지.
- 로컬 `gh auth status`: `lebmouse`, `kwonyoungkwon` 모두 인증 실패. 로컬 Node 26.7.0, pnpm 10.23.0; CI는 Node 20/pnpm 8. 새 의존성 요구사항을 확인해 버전을 통일할 것.
- 현재 개발용 SSE와 Next 전용 구성은 이전 대상에 포함할지 판단 필요. 기존 동작을 검증하기 전 동작한다고 가정하지 않는다.

## 구조 및 기본 선택

- 하나의 저장소와 TanStack Start/React/TypeScript 프로젝트: 공개 글은 빌드 시 정적 생성, `/admin/`은 정적 진입점과 브라우저 UI. 인증 및 쓰기는 별도로 배포한 TypeScript API(우선 Cloudflare Worker 후보).
- GitHub App 사용자 인증 → 허용된 GitHub 사용자 ID 확인 → 서버 측 세션과 GitHub API → `main`에 MDX 커밋 → push Actions → Pages. branch protection 및 GitHub App 사용자 토큰의 권한/트리거를 실제로 확인한다.
- 기본 편집: Markdown/MDX 원문 편집, 제목·날짜·설명·태그·slug, 미리보기, 신규 및 수정, 브라우저 로컬 초안. 공개 저장소의 초안은 GitHub에서 공개됨. 로컬 초안은 기기 간 동기화와 복구를 보장하지 않음.
- `description`은 선택값으로 취급하고 기존 메타데이터를 보존. 이미지 업로드, 관리자에서 삭제, 비공개·기기 간 초안은 범위 결정 필요. 자동 변환이 원문을 손상하지 않도록 한다.
- `main` 직접 커밋은 기본안. 예약 발행이나 PR 검토는 합의 전 포함하지 않음. 기존 글을 발행 테스트에 무심코 덮어쓰지 않는다.
- MDX는 코드 실행 가능성이 있으므로 신뢰 경계와 허용 문법을 정하고, 미리보기에서 임의 코드를 실행하지 않는다. 기존 커스텀 컴포넌트와 GFM/코드 강조 호환성을 실험한다.

## 외부 준비와 확인

1. GitHub: 실제 관리자 계정과 저장소 관리자 권한, Pages source=GitHub Actions, 현재 사이트 URL/커스텀 도메인, branch protection 및 Actions 동작 확인. 로컬 gh 재인증 또는 적절한 연결 필요. 인증 성공을 추정하지 않는다.
2. Cloudflare: 사용할 계정과 Workers 사용 가능 여부, 무료 플랜 범위·제한 및 비용 확인. 로그인/배포 권한과 Worker 이름·주소 확정. 세션 저장소가 필요하면 실제 지원·비용·만료/삭제 방식을 설계한다.
3. GitHub App: 사용자 본인 계정 아래 등록, 이 저장소에만 설치, callback을 실제 Worker URL로 설정. `Contents: write` 및 배포 상태 조회에 필요한 최소 권한 확인. 사용자 ID allowlist, OAuth state/PKCE 및 세션 만료·로그아웃 구현. 서버 시크릿은 Worker secret에 설정하고 채팅·Git·로그에 넣지 않는다.
4. 도메인과 세션: Pages origin과 Worker origin이 다르므로 CORS·CSRF·리다이렉트와 브라우저 서드파티 쿠키 제한 검증. 동작하지 않으면 관리자 UI를 Worker와 같은 사이트에서 제공하는 대안을 검토한다. 어느 경로가 실제로 동작하는지 브라우저에서 확인한다.
5. 배포 접근: Pages와 Worker 배포, App 생성·설치 및 각 계정의 인증/승인에 필요한 접근 제공. 비밀번호·토큰·비밀키를 채팅으로 요청하거나 기록하지 않는다. 기존 사용자 콘텐츠는 보존한다.

### 2026-11-05 — 인증 대안 재검토

- 사용자가 GitHub만으로 가능한지와 이미지 업로드, Workers 무료 범위를 질문. 별도 서버가 필수라는 이전 설명을 정정.
- 대안 1: 저장소 하나에만 Contents 쓰기를 허용한 fine-grained PAT를 사용자가 관리자 UI에 직접 입력하고 브라우저에서 GitHub Contents API 호출. 토큰은 메모리 보관을 기본으로 검토하고 새로고침 시 다시 입력. 앱/XSS가 토큰을 탈취하면 부여된 저장소 권한이 노출됨. 배포 상태 조회는 추가 읽기 권한 필요 여부 확인.
- 대안 2: GitHub App 웹 로그인과 별도 Worker. 토큰 서버 보관과 일반적인 로그인 UX를 제공하지만 별도 계정/배포/세션이 필요. Workers 무료 플랜 요청·CPU 제한과 세션 저장소의 별도 한도 확인.
- GitHub에 이미지 파일 커밋 가능. 업로드 방식, 파일 크기·형식 제한, 저장소 이력 증가와 여러 파일의 커밋·배포 순서 검토. 공개 저장소 이미지는 공개.
- 인증 방식은 아직 사용자 확정 전. 두 방식의 실제 브라우저 API 동작, Pages 및 배포 트리거를 구현 중 검증한다.
